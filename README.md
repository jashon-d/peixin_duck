# MicroDuck 培信战斗手册

> 从驱动层到上位机，全链路自建 MicroDuck 机器鸭。
> 不碰底层永远只会调别人的 SDK —— 我们从硅片写起。

> 📌 **开工必读**：[验收协议 ACCEPTANCE.md](ACCEPTANCE.md)
> 每阶段拆模块，**每模块 ≥90% 专业级考核**才通过；未达标不进入下一阶段。考核记录必须落表。

## 一、项目愿景

复刻并彻底吃透 [立创·泰山派 MicroDuck](https://wiki.lckfb.com/zh-hans/tspi-rk3566/project-case/microduck/image.html) 机器鸭，但**不止于复刻**：

- **自底向上全链路自建**：驱动 → SDK → 控制层 → 通信契约 → 上位机 → 策略部署，每一层都自己写，不依赖官方黑盒 `robotd`。
- **软件升级不改底层**：在驱动/SDK 层定义稳定接口（契约），上层策略、上位机随便换，底层代码纹丝不动。
- **全栈能力养成**：SolidWorks 机械建模 → 嵌入式 C/C++ → 实时控制 → 强化学习 sim2real → 上位机开发，一条线打通。

目标硬件：泰山派 RK3566（ARM64 / Debian 12），14 个 XL330 舵机，IMU LSM6DSV16X。

---

## 二、核心理念（三条铁律）

1. **自底向上，全链路掌控** —— 从 `/dev/ttyS3`、`/dev/i2c-2` 写起，知道每一个字节怎么流。
2. **契约驱动，解耦分层** —— 底层提供稳定 C++ 接口，上层通过契约访问；升级上层不动底层。
3. **每步有证据链** —— 不空谈"已实现"，每完成一步给出：可点击的代码位置 + 关键改动片段 + 单一结论（改了什么、影响什么）。方案选定后不反复横跳。

| 层 | 技术 | 说明 |

- **目标**：在板子到来之前，先把 `microduck_rl → ONNX → 推理` 的链路跑通，吃透策略契约。
- **做什么**：

  2. 吃透 61 维 observation 契约的每一位含义
  3. 吃透 14 维 action 契约和 BAM 电压控制律机理
  4. 用 smoke test 的 checkpoint（`model_4.pt`）导出 ONNX，跑通推理冒烟（验证链路形状，不依赖正式训练）
  5. 产出策略部署契约文档，作为后续写 robotd 的接口规格
  6. 板子到了：SSH 上去抓舵机/IMU 通信波形，逆向官方协议
- **验收标准**：能口述 61D obs 的段位含义 + 14D action 到舵机的变换链路；dummy ONNX 能推理出 14D 输出且形状正确。
- **学到什么**：sim2real 契约思维、ONNX 导出/推理、normalizer bake-in 机理。
- **状态**：🟡 进行中（2026-11-20 冒烟通过：ONNX 导出成功、推理验证 `61→14`、normalizer bake-in 确认；契约见 [docs/policy_deployment_contract.md](docs/policy_deployment_contract.md)。2026-11-25 起按 [ACCEPTANCE.md](ACCEPTANCE.md) 的 A–F 考卷逐模块考核，≥90% 才转 ✅；上板波形侦察待板子刷机后进行）

### ⬜ 阶段 1：驱动层 —— C 语言写用户态驱动

- **目标**：不依赖官方 SDK，自己写 Linux 用户态驱动，直接操作设备文件。
- **做什么**：
  1. UART 半双工驱动（舵机 HD1910，`/dev/ttyS3`）
  2. I2C 驱动（IMU LSM6DSV16X，`/dev/i2c-2`，地址 0x6B）
  3. 先用用户态（`open/read/write` + termios + i2c-dev），不碰内核模块
- **验收标准**：demo 能读 IMU 原始数据（加速度/角速度）、能让单个舵机转到指定角度。
- **学到什么**：Linux 设备文件、termios 串口配置、i2c-dev、并发/阻塞模型。

### ⬜ 阶段 2：SDK 层 —— C++ 封装驱动（契约的起点）

- **目标**：把驱动封装成稳定的 C++ 类接口，对上屏蔽硬件细节。
- **做什么**：
  1. `Servo` 类：`setAngle(id, rad)` / `getAngle(id)`
  2. `IMU` 类：`getAngVel()` / `getAccel()` / `getGravity()`
  3. RAII 资源管理、接口与实现分离
- **验收标准**：上层一行代码 `servo.setAngle(0, 1.57)` 就能转舵机；接口签名冻结（后续不改）。
- **学到什么**：C++ 类设计、RAII、契约思维、接口稳定性。

### ⬜ 阶段 3：控制层 robotd —— C++ 重写

- **目标**：用 C++ 重写官方 `robotd`，实现 50Hz 控制循环，完全掌控底层。
- **做什么**：
  1. 50Hz 实时循环：读传感器 → 跑控制/策略 → 发舵机指令
  2. 集成 ONNX Runtime C++ API 加载策略推理
  3. 实现 DEFAULT_POSE + action×scale 的动作变换
  4. BAM 电压控制律复刻（电池电压影响力矩上限）
- **验收标准**：不用官方 robotd，自己的程序能让鸭子站起来 / 走两步。
- **学到什么**：实时循环、多线程、ONNX Runtime C++、控制理论、sim2real gap 处理。

### ⬜ 阶段 4：通信契约层 —— 实现"不改底层"

- **目标**：定义稳定消息协议，上层通过契约访问 robotd，升级上层不动底层。
- **做什么**：
  1. 定义消息协议（Protobuf / JSON / 自定义二进制）
  2. C++ 网关：对上（手机/上位机）提供服务，对下调用 robotd/SDK 接口
  3. 协议版本管理、向后兼容
- **验收标准**：换一个上位机 App，底层 robotd 一行代码不改，鸭子照动。
- **学到什么**：协议设计、网络编程（TCP/WebSocket）、解耦架构、版本兼容。

### ⬜ 阶段 5：上位机 —— 手机 + 手柄

- **目标**：做出自己的上位机，实时操控 + 监控配置。
- **做什么**：
  1. 手柄蓝牙直连板子（走契约层），实时操控
  2. 手机端（浏览器 Web 或 App）走同局域网，监控遥测 / 调参数 / 切策略
  3. 控制权仲裁（多上位机并存时谁优先）
- **验收标准**：手柄遥杆推一下鸭子动；手机能看遥测、切换 walk/stand 策略。
- **学到什么**：移动端开发、网络通信、控制权仲裁、UX 设计。

### ⬜ 阶段 6：策略部署 —— sim2real 真机验证

- **目标**：把 `microduck_rl` 训练的 ONNX 策略部署到真机，验证 sim2real。
- **做什么**：
  1. 正式训练行走策略（4000~6000 iters）
  2. 导出 ONNX → 部署到 robotd
  3. 真机验证：仿真里学会的走路，真机也能走
  4. 分析 sim2real gap（电压、摩擦、齿隙、延迟）并迭代
- **验收标准**：真机鸭子能稳定行走，跌倒自恢复。
- **学到什么**：模型部署、domain randomization、真机调试、gap 分析方法论。

### 🔄 贯穿：SolidWorks 机械建模理解

- **目标**：读懂现有机械模型，学会从 CAD 到仿真的转换链路。
- **做什么**：
  1. 读懂 `microduck_rl` 里的 `.stl` / `.part` 模型（来源：Onshape 导出）
  2. 理解每个关节的自由度、坐标系、受力
  3. 学会 MJCF/XML 模型描述（刚体、关节、接触力）
- **验收标准**：能解释机器人 14 个关节的布局与运动范围；能修改 MJCF 加一个传感器。
- **学到什么**：机械建模、坐标系变换、刚体动力学、CAD→仿真导出。

## 六、策略部署核心契约（阶段 0 产出）

> 这是后续所有阶段的接口基础，**不可破坏**。来源：`microduck_rl` 源码 + AGENTS.md 交叉验证。

### 61 维 Observation（策略输入）

全策略家族共享，可热插拔。段位严格如下：

| 段位 | 维度 | 内容 | 物理来源 |
|------|------|------|----------|
| `[0:3]` | 3 | `base_ang_vel` | IMU 陀螺仪（机体角速度） |
| `[3:6]` | 3 | `projected_gravity` | IMU 加速度计算的重力方向（机体系） |
| `[6:20]` | 14 | `joint_pos_relative` | 14 舵机当前角 − 默认姿态 |
| `[20:34]` | 14 | `joint_vel` | 14 舵机当前角速度 |
| `[34:48]` | 14 | `last_action` | 上一帧动作 |
| `[48:61]` | 13 | `command` block | `[twist(3), head_pose(4), body_pose(6)]` |

**铁律**：不用的 command slot 必须 zero-pad，**绝对不能删**（删了维度对不上）。

### 14 维 Action（策略输出）

关节顺序锁死（0–4 左腿 / 5–8 头颈 / 9–13 右腿）：
```
0 hip_yaw   1 hip_roll   2 hip_pitch   3 knee    4 ankle     (左)
5 neck_pitch 6 head_pitch 7 head_yaw    8 head_roll           (头颈)
9 hip_yaw  10 hip_roll  11 hip_pitch  12 knee   13 ankle     (右)
```

### Action → 舵机的变换链路

```
action (14D, ~[-1,1])
  → × action_scale
  → + DEFAULT_POSE (14D 参考姿态, 弧度)
  → target_positions 交给 BAM 控制器
  → BAM 固件 PD: (target − measured) × kp → 期望力矩
  → 电压控制律: 力矩受 vin 限制, force_limit = vin × kt / R
  → 电机力矩 → 舵机转动
```

**部署最大的坑**：obs normalizer 由 `export.py` bake 进 ONNX 图（`actor(normalizer(obs))`）。部署端喂给 ONNX 的必须是**原始未归一化**物理量，绝不能手动先归一化（双重归一化 = 策略必崩），也绝不能手动转换 checkpoint（会丢 normalizer）。

### IMU 加速度计符号约定（2026-11-25 复盘）

- `accelerometer` 测的是比力 `a − g`：静止直立时读 `+9.81`，方向**朝上**（地面顶住你）；自由落体时读 0。
- 训练与推理都先取负再归一化：`−accel / |accel|`，得到**朝下**的单位向量，与 `projected_gravity_b` 同向（两条分支必须共享这一约定）。
- 模长 < 0.1 时回退到姿态解算的 `projected_gravity_b`；若主分支不取负，回退前后会出现 180° 跳变。
- 板端接口约定：`IMU::getAccel()` 返回传感器原始系（静止 `+g` 朝上），`IMU::getGravity()` 返回喂给策略的**朝下**单位向量。
